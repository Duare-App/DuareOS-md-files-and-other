# Qavyo OS - Application Features & Requirement Listing

> Last updated: 2026-08-10  
> Scope: Qavyo is moving from a restaurant-only OS to a multi-shop SaaS OS. This file is aligned with the current codebase and separates implemented surfaces from required gaps.

## Current Product Shape

Qavyo currently has these application surfaces:

1. `Qavyo-admin` - platform admin console for owners, tenants, plans, coupons, subscriptions, and platform users.
2. `Qavyo-Server` - restaurant/branch product API mounted under `/api/v1`.
3. `Qavyo-POS` - branch POS app for orders, tills, payments, returns, floor map, reservations, and operator PIN flow.
4. `Qavyo-Inventory` - management app for menu, ingredients, products, services, purchases, staff, reports, settings, expenses, and payroll screens.
5. `Qavyo-kds` - Kitchen Display System app for restaurant kitchen/station workflow.
6. `Qavyo-print-hub` - Flutter/Dart package for claiming backend print jobs and driving thermal printers.
7. `Qavyo-Customer-Website` and `Qavyo-website` - customer/marketing website projects; not yet a unified multi-shop storefront product in the API.

## Status Legend

- **In code** - backed by current routes, schema, or visible app screens.
- **Partial** - UI or schema exists, but backend/domain support is incomplete.
- **Required** - needed for the multi-shop OS direction, but not fully implemented in the current Qavyo code.
- **Future** - product expansion after the multi-shop core is stable.

## 1. Platform Admin & Tenant Control

### 1.1 Platform Admin Console - Partial

The admin app already models Qavyo as a tenant platform, not only as a restaurant tool.

1. Platform login, forgot password, reset password, and authenticated admin layout - **In code in `Qavyo-admin` UI**.
2. Dashboard for platform metrics - **In code in UI**.
3. Owners management - **In code in UI/API client**.
4. Tenants management - **In code in UI/API client**.
5. Administrators/platform users with roles: `SUPER_ADMIN`, `ADMIN`, `DEVELOPER`, `IT`, `SUPPORT`, `MARKETING` - **In code in UI types**.
6. Plan configuration for `FREE`, `BASIC`, `STARTER`, `PROFESSIONAL`, `BUSINESS`, `ENTERPRISE` - **In code in UI/types and main schema**.
7. Coupon management with percentage/flat discounts - **In code in UI/API client**.
8. Subscription overview with status and billing cycle - **In code in UI/types and main schema**.

### 1.2 Control Plane API - Required

`Qavyo-admin` expects `/api/v1/auth/*` and `/api/v1/admin/*`, but the current `Qavyo-Server/src/routes/index.ts` only mounts:

1. `/r/auth`
2. `/restaurants`
3. `/branches`
4. `/inventory/:branchId`
5. `/upload`

Required:

1. Add or connect a platform control-plane backend for `/auth/*` and `/admin/*`.
2. Make tenant creation provision the correct product server/database by business category.
3. Track provisioning status and errors for each tenant.
4. Keep plans, subscriptions, coupons, owners, and platform users in one platform database.
5. Fix tenant update/delete paths so admin actions consistently use the intended backend routes.

## 2. Business Categories & Multi-Shop Direction

### 2.1 Supported Categories in Admin - In code

The admin app currently supports these business category choices:

1. Restaurant & Food
2. Retail & Clothing
3. Electronics & Repair
4. Grocery & Convenience
5. Salon & Spa
6. Hardware & Sanitary
7. Other

The backend stores this as `businessType` text on the tenant/restaurant record, not as a strict database enum.

### 2.2 Multi-Shop Requirement - Required

Qavyo should use "tenant", "business", "shop", and "branch" terminology at the platform layer. Restaurant-specific terms should remain only inside restaurant-specific modules.

Required:

1. Rename platform-facing "Restaurant" labels to "Tenant" or "Business".
2. Use `businessType` as the routing/config key for product behavior.
3. Keep one owner able to manage one or many tenants.
4. Keep branch isolation for every business type.
5. Make module access configurable per tenant.
6. Do not force KDS, tables, recipes, or kitchen concepts onto non-restaurant shops.

## 3. Modules

### 3.1 Product Modules - Partial

Current admin module options:

1. `WEBSITE`
2. `POS`
3. `INVENTORY`
4. `KDS`

Automatic printing is a branch hardware capability. It may become a module or
add-on later, but the current implementation should not depend on browser apps
acting as printer drivers.

Current behavior:

1. Admin stores module selection in tenant settings - **In code**.
2. KDS frontend checks whether `KDS` is enabled and blocks access if disabled - **In code**.
3. POS and Inventory module gating are not fully enforced across product login/access - **Required**.
4. `WEBSITE` is a planned product toggle; the current customer website is still restaurant-oriented - **Partial**.

### 3.2 Required Multi-Shop Modules

1. POS - sales/order checkout for all business types.
2. Inventory - stock, catalog, purchases, vendors, settings.
3. Website - customer-facing catalog/order site where applicable.
4. KDS - restaurant-only kitchen workflow.
5. Automatic printing - branch printer routing for kitchen tickets, expedite tickets, and receipts.
6. Services - service businesses such as salon/spa and electronics repair.
7. Retail products - buy-and-resell shops such as clothing, grocery, hardware, sanitary, electronics.

### 8.3 Automatic Printing - Partial

Automatic printing is no longer only a roadmap item. The backend and Flutter
package have started.

In code:

1. Branch print schema for print hubs, pairing codes, printers, routes, and jobs.
2. Authenticated printer administration under `/api/v1/branches/:branchId/printing`.
3. Hub pairing, claim, report, printer list, and printer status endpoints under `/api/v1/print-hub/:branchId`.
4. `Qavyo-print-hub` Flutter package with REST client, hub polling engine, ESC/POS rendering, network transport, transport registry, and wire models.

Required next:

1. Inventory or POS printer settings UI for agents, printers, routes, test print, retries, and reprints.
2. Thin Android hub app wrapper around `Qavyo-print-hub`.
3. Secure token storage and foreground service behavior.
4. Bluetooth Classic SPP transport and Android permission handling.
5. End-to-end verification for station routing, shared-printer grouping, expedite tickets, per-terminal receipts, leases, retries, expiry, and order/payment commit isolation.

Supported routing requirements:

1. Grill, fryer, drinks, packing/expedite, and POS receipt printers.
2. Station-to-own-printer routing.
3. Multiple stations sharing one printer with grouped ticket sections.
4. Bluetooth printers pinned to the hub they are paired with.
5. Network/LAN/Wi-Fi printers claimable by any branch hub.

Browser apps must not become printer drivers; raw printer I/O belongs in the
native hub layer.
